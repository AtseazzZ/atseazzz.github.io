静态网站发布以后，从首页点进文章通常没什么特别。更值得试的是把文章地址粘到一个新标签页里，再按一次刷新。那时浏览器需要从服务器直接取回这一页，部署路径和构建产物的问题就比较容易露出来。

## 先看构建输出

开发服务器能从源文件提供页面。发布时，我想确认独立的 HTML 已经写进输出目录。因此先运行项目里和发布流程相同的构建脚本，再打开本地预览。

```bash
npm ci
npm run docs:build
npm run docs:preview
```

这座小岛的输出目录是 `.vitepress/dist`。打开它可以看到首页、归档、关于页和 `posts` 下的文章。若浏览器只能通过首页导航找到某篇文章，就再核对那篇文章的 HTML 文件、生成的链接以及服务器处理链接的方式。

## 核对站点的安装路径

用户站点放在 `username.github.io` 的根路径下，VitePress 的 `base` 对应 `/`。如果将来把这套站点迁到账号域名下的项目子路径，页面链接和图片也要带上匹配的前缀。比如文章能显示而站标丢了，可以先在网络面板里看浏览器请求的是哪个路径，再调整资源引用。

我把首页和文章地址记到同一个检查清单里。首页适合看静态资源有没有一起发布，直接打开文章则能确认深层页面的访问方式。两种打开方式各走一遍，比只看首页更容易复现读者遇到的问题。

## 给下一次发布留记录

在 GitHub Pages 上，构建完成后，工作流把生成的文件上传为 Pages 构件，再由部署任务发布。遇到页面没有更新时，我会先查看构件里的文件，再对照部署对应的提交。这样下次只需要记住三个地方：构建目录、站点路径和这次发布的提交。
